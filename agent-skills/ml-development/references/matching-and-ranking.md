# Matching and Ranking

## Start With a Baseline

Establish a measurable baseline before adding semantic models. Good early baselines include normalized skill overlap and TF-IDF cosine similarity.

For a composite score, keep components explicit. Example conceptually:

```text
overall = w_semantic * semantic_similarity
        + w_skills   * skill_overlap
        + w_context  * allowed_context_features
```

Do not invent weights without evaluation. Store/configure weights rather than scattering constants through code.

## Ranking First

Evaluate whether relevant jobs appear near the top, not just whether a score looks plausible in isolation.

Prefer ranking metrics such as Precision@K, Recall@K, NDCG@K, and MRR for recommendation behavior.

## Explainability

Keep enough information to explain recommendations in user-facing terms, for example:

- matched required skills;
- missing required skills;
- optional skills found;
- semantic fit;
- remote/location compatibility when this is a user-selected filter rather than an inferred personal attribute.

Do not claim a probabilistic meaning such as "82% chance of getting hired" unless a separately validated calibrated model actually predicts that outcome. A similarity score is not a hiring probability.

## Data Leakage

Prevent the same or near-identical job postings from appearing across training and evaluation splits.

When using historical snapshots, prefer time-aware splits when the goal is to estimate future recommendation quality.

Do not evaluate against labels generated by the same heuristic being tested and then call the result independent ground truth.

## Embeddings and Caching

Precompute job embeddings in batch when possible. Version embeddings with the model/preprocessing version that produced them.

Do not mix vectors generated by incompatible embedding model versions.

Cache expensive CV representations after upload/processing when the product flow permits it. Invalidate cached representations when relevant CV content or model versions change.

## Filters vs Rank Features

Treat hard user preferences such as selected location, remote-only, or employment type as filters when appropriate instead of silently penalizing jobs with opaque score changes.
