# Migration Rules

## General rules

- Generate or write an Alembic migration for every persistent schema change.
- Review autogenerated migrations before committing them.
- Give migrations concise descriptive revision messages.
- Keep migrations deterministic and independent of local machine state.
- Avoid importing application runtime services into migrations.

## Destructive changes

Treat column/table drops, type narrowing, nullability tightening, and uniqueness additions as potentially destructive.

Before destructive changes:

1. determine whether existing data satisfies the new contract
2. create a backfill/data migration if needed
3. separate incompatible deployment steps when mixed versions can run
4. document any irreversible behavior

## Data migrations

Keep large backfills safe and bounded. Do not make a schema migration perform uncontrolled external API calls.

For large production data changes, prefer a separately observable/retryable migration process when appropriate.

## Verification

Test migration upgrade from the current expected base state. When practical, test downgrade for reversible changes, but do not create fake downgrades that silently lose data just to satisfy symmetry.
